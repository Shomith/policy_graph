# policy_graph

A small, from-scratch experiment: can a graph neural network spot risky AWS IAM
policies better than simple rules, by looking at how actions and resources connect?

This is a learning project. It runs on synthetic data I generated myself, so the
results say something about the method on a controlled benchmark, not about
real AWS accounts.

## What it does

1. Reads an IAM policy (JSON) and turns it into a graph with policy, action and
   resource nodes.
2. Feeds the graph to a 3-layer Graph Attention Network (GATv2) that outputs
   "safe" or "vulnerable" for the whole policy.
3. Compares it against two hand-written rules and two bag-of-actions classifiers.

## Setup

Python 3.11 or 3.12 is the safer choice. I developed on 3.14, where PyTorch prints
a harmless `torch.jit.script` FutureWarning.

Windows (PowerShell):

```
python -m venv venv
venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Windows (cmd): use `venv\Scripts\activate` instead.
Linux / macOS: `source venv/bin/activate`.

## Running it

Run everything from the project root. Use `python -m pg.xxx`, not
`python pg/xxx.py`, otherwise the `pg` imports will fail.

```
# 1. generate the datasets (fixed seeds, so output is reproducible)
python make_data.py          # v1: 196 policies, easy
python make_data_v2.py       # v2: 280 policies, with safe look-alikes

# 2. sanity check that one policy becomes a sensible graph
python test_graph.py

# 3. baselines on the harder dataset
python -m pg.baselines data/policies_v2 data/labels_v2.csv

# 4. train and cross-validate the GNN (saves model.pt)
python -m pg.train data/policies_v2 data/labels_v2.csv

# 5. optional: accuracy per policy family, worst first
python -m pg.analyze data/policies_v2 data/labels_v2.csv
```

Or run steps 1 to 4 in one go: `.\run_all.ps1` (Windows) or `bash run_all.sh`.

## Project layout

```
make_data.py        generates dataset v1 into data/policies
make_data_v2.py     generates dataset v2 into data/policies_v2
test_graph.py       smoke test for the graph builder
run_all.ps1         runs the whole pipeline on Windows
run_all.sh          same, for Linux / macOS
requirements.txt
pg/
  graph.py          policy JSON -> NetworkX -> PyTorch Geometric Data
  model.py          PolicyGAT (3x GATv2, mean+max pooling, MLP head)
  train.py          5-fold grouped cross-validation, saves model.pt
  baselines.py      rule baselines + logistic regression + random forest
  analyze.py        per-family accuracy of the GNN
```

## Graph design

- Nodes: `policy`, `action`, `resource` (a `principal` type is reserved for
  account-level work that isn't built yet).
- Edges: `policy -> action` ("allows") and `action -> resource` ("applies_to"),
  added in both directions so messages can flow both ways.
- Node features (7): one-hot node type, a wildcard flag, a "known escalation
  action" flag, and an admin (`*`) flag.
- Only `Allow` statements are read. `Deny`, `Condition` and `NotAction` are
  ignored.

## Datasets

Both are generated by the scripts above. Each policy is a JSON file; the CSV has
`filename`, `label` (1 = vulnerable) and `family`.

**v1** (196 policies): 96 vulnerable across 16 attack patterns, 100 least-privilege
safe ones. Too easy: every vulnerable policy contains a flagged action and no safe
one does, so any model scores F1 = 1.0 without needing the graph.

**v2** (280 policies, 124 vulnerable):

| Group | Count | Notes |
|---|---|---|
| PassRole on `*` + compute action (Lambda/EC2/CloudFormation/Glue) | 60 | one statement or split across two |
| Single escalation actions on `*` | 48 | CreatePolicyVersion, AttachUserPolicy, etc. |
| `iam:*` and `*` | 16 | |
| Safe: PassRole alone | 20 | look-alike |
| Safe: compute action alone | 24 | look-alike |
| Safe: PassRole on one specific role + compute | 32 | look-alike |
| Safe: ordinary least-privilege | 80 | |

Cross-validation is `StratifiedGroupKFold` grouped by `family`, so every test fold
contains attack families the model never saw during training.

## Results (dataset v2, 5-fold grouped CV)

| Model | Precision | Recall | F1 |
|---|---|---|---|
| Rule: any dangerous action | 0.620 | 1.000 | 0.765 |
| Rule: combo, scope-blind | 0.795 | 1.000 | 0.886 |
| Logistic regression (bag of actions) | 0.000 | 0.000 | 0.000 |
| Random forest (bag of actions) | 0.000 | 0.000 | 0.000 |
| GAT (mean of 5 folds, one seed) | 0.809 | 0.782 | 0.752 |

How to read this:

- The GNN does **not** beat the hand-written combo rule here. That rule was written
  knowing the patterns the generator produces, so its score is flattering.
- The bag-of-actions models score 0 because the grouped split hides whole attack
  families from them; they can't generalise to action names they never saw as
  vulnerable. With a plain random split they would score near 1.0, because variants
  of the same attack would leak across train and test.
- The GNN's recall (0.78) and still-falling training loss suggest it is partly
  undertrained, and it doesn't yet use resource scope as well as it could.
  Per-family analysis (`pg.analyze`) is the next step.
- Single seed, small data: expect fold-to-fold noise of several F1 points.

## Limitations

- Synthetic data only; real policies are messier.
- "PassRole scoped to one role is safe" is a labelling assumption. In real AWS it
  depends on how privileged that role is.
- Static analysis of single policies. No role chaining, trust policies, SCPs,
  permission boundaries or conditions.

## Possible next steps

- Per-family error analysis and more epochs or tuning
- Ablations: GCN vs GAT, with/without edge features, 1 vs 3 layers
- Account-level graphs (users, roles, trust) with attack-path search
- A small CLI that scores a policy file and lists the matched risky actions
