# policy_graph

A small, from-scratch experiment: can a graph neural network spot risky AWS IAM
policies better than simple rules, by looking at how actions and resources connect?

This is a learning project. It runs on synthetic data I generated myself, so the
results say something about the method on a controlled benchmark, not about
real AWS accounts.

## What it does

1. Reads an IAM policy (JSON) and turns it into a graph with policy, action and
   resource nodes.
2. Feeds the graph to a 3-layer Graph Attention Network (GATv2) that outputs
   "safe" or "vulnerable" for the whole policy.
3. Compares it against two hand-written rules and two bag-of-actions classifiers,
   and compares two node-feature sets for the GNN.

## Setup

Python 3.11 or 3.12 is the safer choice. I first developed on 3.14, where PyTorch
prints a harmless `torch.jit.script` FutureWarning.

Windows (PowerShell):

```
python -m venv venv
venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Windows (cmd): use `venv\Scripts\activate` instead.
Linux / macOS: `source venv/bin/activate`.

## Running it

Run everything from the project root. Use `python -m pg.xxx`, not
`python pg/xxx.py`, otherwise the `pg` imports will fail.

```
# 1. generate the datasets (fixed seeds, so output is reproducible)
python make_data.py          # v1: 196 policies, easy
python make_data_v2.py       # v2: 280 policies, with safe look-alikes

# 2. sanity check that one policy becomes a sensible graph
python test_graph.py

# 3. baselines on the harder dataset
python -m pg.baselines data/policies_v2 data/labels_v2.csv

# 4. train and cross-validate the GNN; the last argument picks the feature set
python -m pg.train data/policies_v2 data/labels_v2.csv base      # 7 features per node
python -m pg.train data/policies_v2 data/labels_v2.csv kinds     # 13 features per node

# 5. slower extras, about 15 minutes each on one CPU core
python -m pg.ablate  data/policies_v2 data/labels_v2.csv 5       # both feature sets, 5 seeds
python -m pg.analyze data/policies_v2 data/labels_v2.csv kinds 5 # accuracy per family
```

Or run steps 1 to 4 in one go: `.\run_all.ps1` (Windows) or `bash run_all.sh`.
Recorded outputs of everything above are in `results/`.

## Project layout

```
make_data.py        generates dataset v1 into data/policies
make_data_v2.py     generates dataset v2 into data/policies_v2
test_graph.py       smoke test for the graph builder
run_all.ps1         runs the main pipeline on Windows
run_all.sh          same, for Linux / macOS
requirements.txt
pg/
  graph.py          policy JSON -> NetworkX -> PyTorch Geometric Data (two feature sets)
  model.py          PolicyGAT (3x GATv2, mean+max pooling, MLP head)
  engine.py         train / evaluate / predict for one fold (shared by the scripts below)
  train.py          5-fold grouped cross-validation, saves model.pt
  baselines.py      rule baselines + logistic regression + random forest
  analyze.py        per-family accuracy of the GNN, averaged over seeds
  ablate.py         compares the two feature sets over several seeds
results/            recorded outputs and the environment they were produced in
docs/               project report (Word)
```

## Graph design

- Nodes: `policy`, `action`, `resource` (a `principal` type is reserved for
  account-level work that isn't built yet).
- Edges: `policy -> action` ("allows") and `action -> resource` ("applies_to"),
  added in both directions so messages can flow both ways.
- Only `Allow` statements are read. `Deny`, `Condition` and `NotAction` are
  ignored.

Two node-feature sets:

- **base** (7 features): one-hot node type, a wildcard flag (the name contains `*`),
  a "known escalation action" flag, and an admin (`*`) flag. All 17 escalation
  actions share the one flag, so the model cannot tell `iam:PassRole` from
  `iam:PutRolePolicy`.
- **kinds** (13 features): base plus six 0/1 flags saying what kind of action a node
  is: `passes_role`, `creates_compute`, `edits_permissions`, `makes_credentials`,
  `edits_code`, `assumes_role`. Each of the 17 escalation actions belongs to exactly
  one kind (the code asserts this), and wildcard actions expand (`iam:*` sets several
  kinds). The grouping is my own domain knowledge, see the caveats below.

## Datasets

Both are generated by the scripts above. Each policy is a JSON file; the CSV has
`filename`, `label` (1 = vulnerable) and `family`.

**v1** (196 policies): 96 vulnerable across 16 attack patterns, 100 least-privilege
safe ones. Too easy: every vulnerable policy contains a flagged action and no safe
one does, so the GNN scored F1 = 1.0 without needing the graph.

**v2** (280 policies, 124 vulnerable):

| Group | Count | Notes |
|---|---|---|
| PassRole on `*` + compute action (Lambda/EC2/CloudFormation/Glue) | 60 | one statement or split across two |
| Single escalation actions on `*` | 48 | CreatePolicyVersion, AttachUserPolicy, etc. |
| `iam:*` and `*` | 16 | |
| Safe: PassRole alone | 20 | look-alike |
| Safe: compute action alone | 24 | look-alike |
| Safe: PassRole on one specific role + compute | 32 | look-alike |
| Safe: ordinary least-privilege | 80 | |

Cross-validation is `StratifiedGroupKFold` grouped by `family`, so every test fold
contains attack families the model never saw during training.

## Results (dataset v2)

Mean of the five per-fold scores on identical folds. GNN rows also average over five
seeds (42 to 46) and show the standard deviation across seeds.

| Method | Precision | Recall | F1 |
|---|---|---|---|
| Rule: any dangerous action | 0.620 | 1.000 | 0.764 |
| Rule: combo, scope-blind | 0.804 | 1.000 | 0.888 |
| Logistic regression (bag of actions) | 0.000 | 0.000 | 0.000 |
| Random forest (bag of actions) | 0.000 | 0.000 | 0.000 |
| GAT, base features (7) | 0.849 ± 0.019 | 0.744 ± 0.029 | 0.766 ± 0.013 |
| GAT, kinds features (13) | 0.941 ± 0.004 | 0.940 ± 0.013 | 0.940 ± 0.008 |

| Fold | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| base | 0.520 | 0.874 | 0.838 | 0.807 | 0.789 |

### Where the model fails (accuracy per family, averaged over 5 seeds)

| Family | base | kinds |
|---|---|---|
| vuln_single_updatefunctioncode | 0.03 | 0.10 |
| vuln_single_putrolepolicy | 0.08 | 1.00 |
| vuln_single_attachuserpolicy | 0.33 | 1.00 |
| vuln_single_updateloginprofile | 0.53 | 1.00 |
| vuln_single_createaccesskey | 0.65 | 1.00 |
| vuln_single_createpolicyversion | 0.80 | 1.00 |
| vuln_iam_wildcard | 0.58 | 1.00 |
| safe_compute_alone (lambda / cfn / glue / ec2) | 0.07 / 0.13 / 0.50 / 0.60 | 1.00 each |
| safe_scoped_passrole_cfn | 0.80 | 1.00 |
| safe_passrole_alone | 0.96 | 0.65 |

Every family not listed scores 0.925 or higher with base features and 1.00 with kinds
(the PassRole + compute combinations, the `*` admin policy, the other scoped-PassRole
look-alikes, and all 80 ordinary safe policies). Full tables are in `results/`.

### How to read this

- **Scope is not the problem.** With base features the model already handles the
  scoped-PassRole look-alikes (0.80 to 1.00), which a scope-blind rule gets wrong.
- **The base features hide which action it is.** All escalation actions carry the same
  flag, so a lone `lambda:CreateFunction` (safe) and a lone `iam:PutRolePolicy`
  (vulnerable) look the same to the model. Training loss at epoch 40 stays around
  0.26 to 0.33 with base features and drops to 0.001 to 0.013 with kinds, which points
  to missing information rather than too little training (seed 42, see `results/train_*.txt`).
- **Kinds fixes most of it, but only where a kind has siblings.** Families whose kind
  also appears in other folds are learned. `lambda:UpdateFunctionCode` is the only
  action of its kind, so it never appears in training when its family is held out
  (accuracy 0.10). Almost all remaining error comes from two families: those missed
  UpdateFunctionCode policies and false alarms on `safe_passrole_alone`, which sits
  entirely in fold 1 so the model never sees PassRole on its own during training.
- **Against Rule B:** the kinds model has the higher F1 (0.940 vs 0.888), mostly from
  precision (0.941 vs 0.804, because it leaves the scoped look-alikes alone). Its
  recall is lower (0.940 vs 1.000).
- The bag-of-actions models score 0 because the grouped split hides whole attack
  families from them. With a plain random split I expect them to score near 1.0, but
  I have not run that.

### Caveats that matter

- The kinds features were designed **after** looking at the base model's errors on
  these same folds, so 0.940 is optimistic. A fresh test set with unseen kinds is
  needed before believing it.
- The six kinds encode the same grouping Rule B uses, so the gain is bought with
  expert knowledge, not discovered by the model.
- Rule B was written knowing the patterns the generator produces.
- Five seeds vary initialisation and batch order only. The folds are the same every
  time.
- Results in `results/` come from a Linux CPU environment (see `results/README.md`).
  An earlier Windows run with the same seed differed slightly.

## Limitations

- Synthetic data only; real policies are messier. In the generator, vulnerable
  patterns are always applied to `*`.
- "PassRole scoped to one role is safe" is a labelling assumption. In real AWS it
  depends on how privileged that role is.
- Static analysis of single policies. No role chaining, trust policies, SCPs,
  permission boundaries or conditions.
- The wildcard flag fires on any asterisk, including partial patterns like
  `bucket/*`.
- No hyperparameter tuning, no validation set.

## Possible next steps

- A fresh dataset (new seed, new escalation kinds) generated after the feature set is
  frozen, as a real held-out test
- Handle single-member kinds, for example by learning action representations instead
  of hand-grouping
- Ablations: GCN vs GAT, with/without edge features, 1 vs 3 layers, with/without the
  hand-made "dangerous" flag
- Account-level graphs (users, roles, trust) with attack-path search
- A small CLI that scores a policy file and lists the matched risky actions
